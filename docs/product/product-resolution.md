# Product Resolution

> Phase 4 of `docs/program/MASTER-PROMPT.md`. Defines the normalized Product Resolution model and the resolution ladder that turns a pasted Amazon UAE URL into a trustworthy priced product (J1/J2 in `docs/ux/journey-map.md`). **This formalizes and extends an already-built engine — it does not design one from scratch.** `platform/packages/commerce/src/{types,resolution,strategies,marketplace}.ts` already implement a 4-tier ladder (`api → structured → vision → manual`), a per-field confidence/provenance model, and a cost-budgeted escalation pipeline that closely matches this program's intent. See `docs/architecture/product-resolution-architecture.md` for the code-level detail; this document is the product/data-model layer above it.

## Method note

Per MASTER-PROMPT §1/§2, this phase used repository evidence first (existing `@xb/commerce` package, `technical-blueprint-v1.md`, `feasibility-revalidation-v0.2.md`), then external research where the repo was silent: live fetches against `amazon.ae` PDPs and the official Amazon Product Advertising API documentation. The live fetches are reported honestly below, including where they failed — a failed fetch against Amazon's own anti-bot layer is itself evidence about what the resolution ladder must survive, not a gap in this research.

## The normalized model

Canonical shape, `ResolvedProduct` (`platform/packages/commerce/src/types.ts:10-29`): `marketplace`, `externalProductId`, `canonicalUrl`, `title`, `seller`, `brand`, `variant`, `imageUrl`, `price` (`Money`), `available`, `weightKg`, `dimensionsCm`, `category`, `route`, `provenance`, `observedAt`. Every marketplace normalizes to this one shape so the quote engine and both frontends never learn Amazon and Noon describe a product differently (code comment, `types.ts:5-9`).

**Fields already present that satisfy MASTER-PROMPT §PHASE 4's wishlist:** marketplace, canonical URL, ASIN (as `externalProductId`), title, brand, selected variation (`variant`), one image (`imageUrl`), seller, price, currency (via `Money`), availability, weight/dimensions (chargeable-weight proxy for shipping), category, and **field-level provenance/confidence** — the wishlist's "provenance/confidence of important fields" isn't a nice-to-have here, it's already the central mechanism (`FieldProvenance`, `types.ts:33-50`).

**Fields the wishlist names that don't exist yet — confirmed gap, not assumption:**

| Field | Why it matters | Priority |
|---|---|---|
| `selectableVariations` (the full option set, not just the chosen one) | J1's "multiple variations → picker" alternate path needs to render options *before* a variant is chosen — today `variant` only records what's already selected. | High — blocks J1's variation-picker UI directly. |
| `fulfillmentParty` (distinct from `seller`) | Amazon UAE's real distinction is "Sold by X, Fulfilled by Amazon" vs. "Sold by X, Fulfilled by X" — these carry different delivery-reliability risk and belong in the landed-cost risk model, not just display copy. | High — feeds `resolutionRiskFactor`-style logic. |
| `itemCondition` | Amazon UAE lists used/renewed items in some categories; a used item silently priced as new is a customer-trust failure. | Medium. |
| `originalPrice` / `discountPercent` | Confirmed present on real listings (Mega Sale / White Friday event pages advertise "up to 50–70% off"); today's model only has final `price`, losing the "is this actually a deal" signal that matters for trust/conversion copy. | Medium. |
| `quantityRestrictions` (max-per-order) | Amazon enforces per-order quantity caps on some SKUs; procuring above the cap silently fails at purchase time rather than being caught at resolution. | Medium — ties to the max-procurement-price guard's sibling risk. |
| `estimatedMarketplaceDelivery` | Needed to compose the customer-facing delivery estimate (this platform's own logistics estimate must add to, not replace, the marketplace's own dispatch lead time). | Medium. |
| `eligibility`/`restrictions` (e.g. shipping-restricted categories, age-restricted items) | Some categories are legally or logistically inadmissible for cross-border personal import; resolving them successfully but failing at customs is worse than catching it at resolution. | High — ties directly to the compliance RULE (`CLAUDE.md`) and I5's job (J14, `journey-map.md`). |

**Recommendation:** add these as optional fields on `ResolvedProduct` with their own `FieldProvenance` entries, not a parallel structure — the existing per-field confidence mechanism already generalizes to them without redesign. Not added in this pass because Phase 4 is discovery/design, not implementation (MASTER-PROMPT's own phase boundary).

## The resolution ladder — formalized

MASTER-PROMPT's suggested ladder (authoritative API → structured metadata → PDP extraction → browser extraction → vision-assisted → customer confirmation → operator review) is **already implemented as four cost-ordered strategies**, with two of MASTER-PROMPT's named stages folded in rather than separate:

1. **`api` tier** (cost 1) — official marketplace product API. **EXTERNAL-GATE, and newly time-sensitive** (see "New finding" below).
2. **`structured` tier** (cost 3) — JSON-LD/schema.org extraction from the fetched page. "PDP extraction" and "browser extraction" are not separate rungs in the code — fetching the page (`PageFetcher.fetchHtml`) is a mechanism *inside* this tier and the vision tier, not its own escalation step. This is a reasonable collapse: MASTER-PROMPT's 7-stage list describes a *conceptual* gradient, and folding "structured extraction" and "the browser fetch it depends on" into one tier is simpler without losing a decision point — the pipeline doesn't need to decide separately "should I fetch the page" vs. "should I parse it structurally," those always happen together.
3. **`vision` tier** (cost 20) — screenshot/HTML to a vision-capable model, confidence explicitly capped below the two tiers above it.
4. **`manual` tier** (cost 50) — operator-supplied values, confidence forced to 1.0 (an operator's word is the ceiling of trust in this system, correctly).

**One real gap against MASTER-PROMPT's ladder: "customer confirmation" is not a resolution tier at all today.** The pipeline escalates on missing/low-confidence *required* fields, but never asks the *customer* to confirm an already-resolved-but-uncertain field (e.g., a vision-tier weight estimate). J1 in `journey-map.md` already flags this ("field-level provenance/confidence badges — GAP, Phase 4 dependency"). **Recommendation, recorded per MASTER-PROMPT §1:** add customer confirmation as a UI-layer behavior gated on `provenance[field].confidence < <a threshold above MIN_FIELD_CONFIDENCE>`, not as a fifth pipeline tier — the pipeline's job is producing the best available answer with honest confidence; asking the customer to confirm a low-but-usable-confidence field is a frontend decision about trust presentation, not a resolution strategy. **Confidence: medium** (a reasonable architectural split, but not verified against how `NEEDS_REVIEW` vs. a hypothetical lower "customer-should-confirm" band would need to differ in the pipeline's status logic). **Reversal cost: low** — purely additive, no existing field or type changes.

**Escalation mechanics** (`ResolutionPipeline`, `resolution.ts:50-297`): strategies run cheapest-first by `costUnits`; the pipeline escalates to the next tier only when `REQUIRED_FIELDS` (`title`, `price`, `available`, `weightKg`, `category`) are still missing or below `MIN_FIELD_CONFIDENCE = 0.5`; results merge field-by-field keeping the *highest-confidence* answer per field, not the *last* tier's answer — meaning a cheap API hit for `price` survives even if a later vision-tier call also returns a (less confident) price. A cost budget caps total escalation. Outcome is `RESOLVED | NEEDS_REVIEW | FAILED`.

## Non-fabrication rules (MASTER-PROMPT explicit requirement)

Never fabricate price, variation, availability, shipping, seller, or delivery estimate. This is already structurally enforced, not just a policy statement: every field carries a `FieldConfidence{tier, strategy, confidence}` (`types.ts:33-38`), a field below `MIN_FIELD_CONFIDENCE` is **treated as missing**, not as a low-quality-but-present value (`types.ts:62` comment), and `REQUIRED_FIELDS` cannot resolve to `RESOLVED` status while any are missing/low-confidence — the outcome becomes `NEEDS_REVIEW` or `FAILED` instead. The customer-facing consequence (`ProductCard.tsx` weight-confidence hint, `apps/web/app/page.tsx:138-143`'s Persian "some info like weight is uncertain" warning on `NEEDS_REVIEW`) already reflects this rather than silently presenting a guess as fact.

**Where this needs to extend, not change:** the new fields above (§"Fields... don't exist yet") must each get their own confidence entries and participate in the same missing-vs-present logic — e.g., an unconfirmed `fulfillmentParty` should not silently default to "fulfilled by seller" (the riskier assumption) or "fulfilled by Amazon" (the reassuring one); it should be `undefined` and shown as unconfirmed, exactly as the model already treats other unresolved fields.

## Empirical findings from this pass

**1. Amazon UAE actively resists plain HTTP fetching — confirmed firsthand, not assumed.** Seven live fetch attempts against `amazon.ae` PDP and search URLs this session: six returned `503 Service Unavailable`, one returned only page-shell/analytics markup with no product body. This directly corroborates an existing code comment (`apps/api/src/composition/adapters.ts:300-304`, per the codebase-research pass this phase ran in parallel) that the `structured`/`vision` strategies are "blocked on... a fetcher the marketplace will not block, not on code." **This is now empirically confirmed, not just anticipated.** Implication for Phase 10/12: the `structured` tier's `PageFetcher` needs a fetching mechanism resilient to Amazon's bot-detection (realistic browser fingerprint/session, or a licensed fetching/scraping provider sitting behind the same port-and-adapter pattern as every other external dependency) — a bare server-side `fetch()` is confirmed insufficient today, not merely a theoretical risk.

**2. New material fact, not previously recorded: the official Amazon Product Advertising API (PA-API 5.0) — the presumed backing for the `api` tier — is deprecated as of May 15, 2026, superseded by a "Creators API" with a narrower access model (requires an active Amazon Associates account with recent qualifying sales, per Amazon's own documentation).** As of this session's date (2026-08-14), PA-API is already past its deprecation date. `marketplace.ts:78` marks `amazon.ae`'s `productApi: true` and `adapters.ts` describes the `api` tier as "blocked on credentials," which reads as "just needs a business relationship" — the external reality is now sharper: the credential path envisioned may no longer be obtainable as originally designed, and needs re-evaluation against the successor Creators API's actual capabilities (which this pass did not investigate in depth — flagged, not resolved). **Recorded as a contradiction per MASTER-PROMPT §5 (never silently resolve):** existing code/docs assume `api`-tier viability is a credentials/business question; new external evidence says it may be an availability question. **Confidence: high that PA-API is deprecated (directly from Amazon's own docs); medium on the practical impact**, since Creators API's product-data capabilities weren't evaluated this pass. **Reversal cost: low to record now, but this should block treating the `api` tier as "just needs a contract signed" in Phase 10/12 planning without re-checking Creators API first.**

**3. Real PDP structural evidence gathered via search-index snippets (Google's cache of Amazon UAE listings), since direct fetch was blocked:**
- **Variations** genuinely appear as compound title/URL data on real listings, e.g. a Ray-Ban listing titled "...Color: Silver/Blue Photochromic, Size: 58 mm" — confirms color+size as a common two-axis variation pattern to design the picker around.
- **Multi-seller** listings expose an "Other sellers on Amazon" panel with a count and a starting price (e.g. "Other sellers on Amazon · New (7) from AED262.42") — confirms seller/price are plural-by-nature per product, not a single fixed pair; the model's `seller: string` (singular) is correct for *the resolved offer*, but a "which offer among several" decision (MASTER-PROMPT's "default to the authoritative/lowest-risk offer, show alternatives," already noted in `journey-map.md` J1) needs the plural view somewhere upstream of the singular `ResolvedProduct`.
- **Unavailability** uses the exact, consistent copy "Currently unavailable. We don't know when or if this item will be back in stock." across categories — a strong, stable signal string worth using as a structured-extraction anchor (in addition to any availability microdata) and worth distinguishing in copy from the *post-purchase* `OUT_OF_STOCK` exception state's copy (`order-state-machine.ts` `ALERTS.OUT_OF_STOCK`) — these are different moments (never-purchasable vs. sold-out-after-we-tried-to-buy-it) and should read differently to the customer even though both mean "you won't get this."
- **Discounts** are marketed at the percentage level (site-wide "Mega Sale... up to 50% off," "White Friday... up to 70% off"); individual PDPs are understood (from general Amazon marketplace structure, not confirmed via direct fetch this session — see limitation below) to show a strikethrough original price alongside the current price. Feeds the `originalPrice`/`discountPercent` field gap above.

**4. "Prime/FBA" (MASTER-PROMPT's phrasing) does not map literally onto Amazon UAE — recorded assumption.** Amazon UAE does not market a "Prime" membership badge the way amazon.com does. The equivalent real distinction on Amazon UAE is **"Fulfilled by Amazon" (FBA) vs. seller-fulfilled** — this is the `fulfillmentParty` field gap above, not a separate concept. **Confidence: high** (general, stable Amazon marketplace-mechanics knowledge). **Reversal cost: low** — purely a naming/interpretation clarification, no model impact beyond the already-flagged `fulfillmentParty` field.

**5. Limitation, stated plainly:** this pass did not achieve live, rendered access to an actual Amazon UAE PDP body (finding #1). Structural claims about single-vs-multi-image galleries, exact FBA badge placement, and exact discount-badge markup are therefore inferred from general Amazon marketplace-structure knowledge and search-snippet evidence, not confirmed against a rendered UAE page this session. This should be re-verified with an actual browser-capable fetch (e.g. via a connected browser-automation MCP, not available in this session) before Phase 5 commits to pixel-level layout decisions for the confirmation screen.
